学习 AI 开发时，我不想只停留在“看懂了”的阶段，而是希望每学到一个工具，就能留下一个真实可运行的作品。这个博客就是第一个小作品。

它的目标很简单：用 Markdown 写文章，用 Astro 生成静态网页，再在本地浏览器中看到结果。但它也把 AI 开发里几个很重要的习惯串到了一起：明确目标、让工具执行、检查结果、把过程沉淀下来。

## 从一个明确任务开始

这次任务不是泛泛地说“做一个网站”，而是拆成了可以验收的条件：

1. 在 WSL 的 `~/study/blog` 创建 Astro 项目；
2. 写一篇 `Hello World` Markdown 文章；
3. 在首页放上文章入口；
4. 启动本地服务，并确认 `http://localhost:4321` 能访问。

这种描述方式对人和 AI 都很友好。目标、位置、技术选择和验收标准都写清楚后，执行过程就不容易跑偏。AI 可以负责生成初始结构、解释命令和排查错误；我则负责确认范围，并对最终结果负责。

## 把开发环境当作项目的一部分

我选择把项目放在 WSL 的 Linux 文件系统里，而不是直接放在 Windows 挂载盘中。这样安装依赖、文件监听和运行开发服务器通常会更稳定。

同时，Windows 和 WSL 并不是两个孤岛。以后如果需要从 GitHub 获取模板或资料，可以先在 Windows 中下载到 `F:\situ\bridge`，再通过 WSL 中对应的 `/mnt/f/situ/bridge` 复制到项目目录。这个 bridge 文件夹相当于两套环境之间的中转站：

```text
GitHub → F:\situ\bridge → /mnt/f/situ/bridge → ~/study/blog
```

这次尝试连接 GitHub 时，网络仍然无法访问 `github.com`。这不是“跳过问题”的理由：先记录限制，继续完成可以离线完成的部分，网络恢复后再补充模板资源，才是更可靠的开发节奏。

## AI 是协作者，不是替代验证的按钮

在这个小项目中，AI 能帮我快速生成页面、内容集合和样式，但每一次改动都需要回到命令行验证：

```bash
cd ~/study/blog
npm run build
npm run dev
```

`npm run build` 确认网站能输出静态文件；`npm run dev` 让我在浏览器中检查首页和文章页。只有命令通过、页面实际可访问，任务才算完成。

我希望以后也维持这个流程：让 AI 提高实现速度，但不把“它说完成了”当成完成。编译、测试、浏览器检查和代码复查，仍然是开发者必须保留的判断环节。

## 下一步

这个博客现在只有两篇文章，但它已经是一个可扩展的起点。接下来可以继续：

- 为文章增加封面图、目录和更多标签；
- 从 bridge 引入合适的 Astro 博客模板作为视觉参考；
- 用 Git 管理每次内容与功能的变化；
- 记录更多 AI 工具的真实使用心得，而不只记录结论。

先完成一个小而完整的闭环，再逐步变得更好。这就是我学习 AI 开发的第一条原则。
